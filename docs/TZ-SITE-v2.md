## 1. Обзор платформы

**TaskBridge** -- это маркетплейс фриланс-заданий для цифровых услуг, ориентированный на малый бизнес. Платформа соединяет двух участников:

- **Заказчик (Client)** -- имеет задачу/проект, нуждается в специалисте. Публикует задание, рассматривает отклики, выбирает исполнителя, получает результат.
- **Исполнитель (Performer)** -- обладает навыками, хочет заработать. Просматривает задания, подаёт отклики, получает выбор, выполняет работу, получает оплату напрямую.

Платформа обеспечивает соединение и предоставляет инструменты для взаимодействия. Платформа **НЕ посредничает в оплате** (в текущей версии) и **НЕ берёт комиссию** с сделок между пользователями.

### Ключевые принципы

| Принцип | Описание |
|---------|----------|
| Нулевая комиссия | Платформа не берёт процент с сделок. Заказчик и исполнитель договариваются об оплате напрямую |
| Свободный инструмент | TaskBridge -- бесплатный инструмент для обеих сторон |
| Приватность чата | Администратор не имеет доступа к содержимому личных чатов |
| Прозрачность рейтингов | Рейтинги формируются исключительно на основе реальных отзывов |
| CPM-монетизация | Единственный источник дохода платформы -- баннерная реклама (CPM) |

## 2. Бизнес-модель

### 2.1 Источник дохода

**Единственный источник дохода владельца платформы -- CPM-реклама** (баннерные объявления, показываемые посетителям).

```
Доход владельца = Показы рекламы x CPM-ставка / 1000
```

### 2.2 Что платформа НЕ делает

- **НЕ** берёт комиссию с сделок между пользователями (0%)
- **НЕ** удерживает средства (нет эскроу в текущей версии)
- **НЕ** навязывает платные тарифы пользователям
- **НЕ** ограничивает функциональность платными подписками

### 2.3 Философия монетизации

> Заказчики получают результат, исполнители получают оплату -- платформа не берёт ничего. Проблема дохода владельца -- это его собственная проблема (реклама), а не проблема пользователей.

Пользователи приходят на платформу за ценностью: найти специалиста или найти работу. Реклама -- это компромисс, позволяющий предоставлять платформу бесплатно.

### 2.4 Рекламные места (планируемые)

| Место | Формат | Условие показа |
|-------|--------|----------------|
| Лендинг (главная для гостей) | Баннер 728x90, 300x250 | Всегда |
| Список заданий (сайдбар) | Баннер 300x250 | Всегда |
| Страница задания | Баннер 728x90 под описанием | Всегда |
| Каталог исполнителей | Нативный баннер между карточками | Каждые 10 карточек |
| Личный кабинет | Баннер 728x90 | Только для неавторизованных (если возможен гостевой доступ) |

## 3. Целевая аудитория

### 3.1 Заказчики

- Владельцы малого и микро-бизнеса
- Индивидуальные предприниматели
- Стартапы без собственного IT-отдела
- Частные лица с разовыми цифровыми задачами

**Типичные задачи:** сайт для бизнеса, дизайн логотипа, настройка рекламы, Telegram-бот, автоматизация процессов, копирайтинг, презентации, аналитика.

### 3.2 Исполнители

- Фрилансеры (веб-разработчики, дизайнеры, маркетологи)
- Начинающие специалисты, нарабатывающие портфолио
- Специалисты среднего уровня, ищущие дополнительные заказы
- Небольшие студии и агентства

## 4. Технологический стек

### 4.1 Backend

| Компонент | Технология | Обоснование |
|-----------|-----------|-------------|
| Среда выполнения | Node.js (>= 18.x) | Асинхронная модель, быстрый I/O, большая экосистема |
| HTTP-фреймворк | Express.js 4.x | Минимализм, гибкость, огромное количество middleware |
| База данных | SQLite 3 (через better-sqlite3) | Нулевая конфигурация, файловая БД, высокая скорость чтения |
| Режим БД | WAL (Write-Ahead Logging) | Параллельные чтения без блокировок записи |
| Аутентификация | JWT (jsonwebtoken) | Stateless-токены, 7-дневный срок действия |
| Хеширование паролей | bcrypt (bcryptjs) | Адаптивная сложность, защита от rainbow-table |
| Загрузка файлов | multer | Валидация типа и размера, сохранение на диск |
| Валидация входных данных | Ручная (без внешних библиотек) | Минимализм зависимостей для MVP |
| CORS | cors middleware | Разрешение cross-origin запросов для SPA |

### 4.2 Frontend

| Компонент | Технология | Обоснование |
|-----------|-----------|-------------|
| Архитектура | SPA (Single Page Application) | Один HTML-файл, hash-based routing |
| JavaScript | Vanilla JS (ES2020+) | Нет сборщика, нет фреймворка, мгновенная загрузка |
| CSS-фреймворк | Tailwind CSS (CDN) | Утилитарный CSS, нет кастомных стилей |
| Иконки | Heroicons / Lucide (CDN) | SVG-иконки по требованию |
| Шрифты | Inter (Google Fonts CDN) | Современный sans-serif, хорошая читаемость |
| HTTP-клиент | fetch API | Нативный, без зависимостей |

### 4.3 Административная панель

| Компонент | Описание |
|-----------|----------|
| Отдельное приложение | Запускается на порту 3001 |
| Доступ | Только для пользователей с ролью `admin` |
| Функциональность | Управление пользователями, заданиями, жалобами, модерация |

## 7. Аутентификация и авторизация

### 7.1 Регистрация

**Endpoint:** `POST /api/auth/register`

**Процесс:**
1. Пользователь заполняет форму: email, пароль, имя, роль (`client` или `performer`)
2. Сервер валидирует: email уникален, пароль >= 6 символов, роль допустима
3. Пароль хешируется через bcrypt (salt rounds = 10)
4. Создаётся запись в таблице `users`
5. Создаётся профиль (в `client_profiles` или `performer_profiles`)
6. Генерируется JWT-токен
7. Отправляется уведомление типа `welcome`
8. Ответ содержит токен и данные пользователя

**Пароль:**
- Минимальная длина: 6 символов
- Хеширование: bcrypt с salt rounds = 10
- Хранение: только хеш, оригинальный пароль не хранится

**Подтверждение email:** НЕ требуется в MVP. Пользователь получает доступ сразу после регистрации.

### 7.2 Вход (Login)

**Endpoint:** `POST /api/auth/login`

**Процесс:**
1. Пользователь отправляет email и пароль
2. Сервер находит пользователя по email
3. Проверяет, что пользователь не заблокирован (`status != 'blocked'`)
4. Сравнивает пароль с хешем через bcrypt.compare()
5. При успехе генерирует JWT-токен
6. Возвращает токен и данные пользователя

### 7.3 JWT-токен

| Параметр | Значение |
|----------|----------|
| Алгоритм | HS256 |
| Секретный ключ | Из переменной окружения `JWT_SECRET` |
| Срок действия (expiresIn) | 7 дней (`7d`) |
| Payload | `{ id, email, role }` |
| Заголовок | `Authorization: Bearer <token>` |

### 7.4 Смена пароля

**Endpoint:** `PUT /api/auth/password`

**Требования:** Аутентифицированный пользователь (JWT).

**Процесс:**
1. Пользователь отправляет текущий пароль и новый пароль
2. Сервер проверяет текущий пароль
3. Хеширует новый пароль
4. Обновляет запись в БД

### 7.5 Middleware аутентификации

```javascript
// Принцип работы middleware
function authenticate(req, res, next) {
  const token = req.headers.authorization?.replace('Bearer ', '');
  if (!token) return res.status(401).json({ error: 'Требуется аутентификация' });

  try {
    const decoded = jwt.verify(token, JWT_SECRET);
    // Проверяем, что пользователь не заблокирован
    const user = db.prepare('SELECT status FROM users WHERE id = ?').get(decoded.id);
    if (!user || user.status === 'blocked') {
      return res.status(403).json({ error: 'Аккаунт заблокирован' });
    }
    req.user = decoded;
    next();
  } catch (err) {
    return res.status(401).json({ error: 'Недействительный или истёкший токен' });
  }
}
```

### 8.4 Расчёт рейтинга

Рейтинг рассчитывается как **средневзвешенное значение** по всем полученным отзывам:

```
rating = SUM(rating_i) / COUNT(reviews)
```

Где `rating_i` -- оценка от 1 до 5, поставленная в отзыве. Обновляется при каждом новом отзыве.

### 9.5 Жизненный цикл задания (State Machine)

```
                        ┌──────────────┐
                        │    draft     │  ←─── Создание
                        │   (черновик) │
                        └──────┬───────┘
                               │ Опубликовать
                               ▼
                        ┌──────────────┐
                        │  published   │  ←─── Видно всем
                        │ (опубликовано)│
                        └──────┬───────┘
                               │ Модерация (админ)
                               ▼
                        ┌──────────────┐
                        │  moderation  │  ←─── Проверка админом
                        │ (модерация)  │
                        └──────┬───────┘
                               │ Одобрить + Исполнитель выбран
                               ▼
                        ┌──────────────┐
                        │   assigned   │  ←─── Исполнитель назначен
                        │  (назначен)  │
                        └──────┬───────┘
                               │ Исполнитель начинает работу
                               ▼
                        ┌──────────────┐
                        │ in_progress  │  ←─── Работа идёт
                        │ (в работе)   │
                        └──────┬───────┘
                               │ Исполнитель сдал работу
                               ▼
                        ┌──────────────┐
                        │   review     │  ←─── Заказчик проверяет
                        │  (проверка)  │
                        └──────┬───────┘
                               │ Заказчик принял
                               ▼
                        ┌──────────────┐
                        │  completed   │  ←─── Задание завершено
                        │  (завершено) │
                        └──────┬───────┘
                               │ Через 90 дней
                               ▼
                        ┌──────────────┐
                        │   archived   │  ←─── Архив
                        │  (архив)     │
                        └──────────────┘

  ┌─────────────────────────────────────────────────────────┐
  │  Из ЛЮБОГО активного статуса возможен переход:          │
  │                                                         │
  │  any active → cancelled (отменено)                      │
  │  any status → disputed (через жалобу / report)          │
  │  completed/cancelled → archived (через 90 дней)         │
  └─────────────────────────────────────────────────────────┘
```

#### 9.5.1 Таблица переходов статусов

| Из статуса | В статус | Кто может | Условия | Уведомления |
|------------|----------|-----------|---------|-------------|
| `draft` | `published` | Заказчик (владелец) | Задание заполнено (title, description, category обязательны) | -- |
| `published` | `moderation` | Админ | -- | -- |
| `published` | `assigned` | Заказчик | Принят отклик исполнителя | `offer_accepted` исполнителю |
| `published` | `cancelled` | Заказчик (владелец) | -- | Отклики получают `offer_rejected` (если были) |
| `moderation` | `published` | Админ | Задание одобрено после проверки | Заказчику: system notification |
| `moderation` | `cancelled` | Админ | Задание нарушает правила | Заказчику: system notification с причиной |
| `assigned` | `in_progress` | Исполнитель | Исполнитель подтверждает начало работы | Заказчику: system notification |
| `assigned` | `cancelled` | Заказчик или Исполнитель | -- | Второй стороне: system notification |
| `in_progress` | `review` | Исполнитель | Исполнитель сдал работу | Заказчику: system notification |
| `in_progress` | `cancelled` | Заказчик или Исполнитель | -- | Второй стороне: system notification |
| `review` | `completed` | Заказчик | Заказчик принял работу | Исполнителю: `task_completed` |
| `review` | `in_progress` | Заказчик | Заказчик вернул на доработку | Исполнителю: system notification |
| `review` | `cancelled` | Заказчик | -- | Исполнителю: system notification |
| `completed` | `archived` | Система (cron/ручной) | Прошло 90 дней с `completed_at` | -- |
| `cancelled` | `archived` | Система (cron/ручной) | Прошло 90 дней с `updated_at` | -- |
| Любой | `disputed` | Любой участник (через report) | Подана жалоба | Админу: system notification |

#### 9.5.2 Определения статусов

| Статус | Описание |
|--------|----------|
| `draft` | Черновик. Видит только заказчик-владелец. Можно редактировать и удалить |
| `published` | Опубликовано. Видно всем пользователям. Исполнители могут подавать отклики |
| `moderation` | На модерации. Админ проверяет соответствие правилам |
| `assigned` | Исполнитель назначен. Открывается чат. Новые отклики не принимаются |
| `in_progress` | В работе. Исполнитель выполняет задание |
| `review` | На проверке. Исполнитель сдал результат, заказчик проверяет |
| `completed` | Завершено. Работа принята. Обе стороны могут оставить отзыв |
| `cancelled` | Отменено. Задание закрыто без завершения |
| `disputed` | Спор. Открыта жалоба, требуется вмешательство админа |
| `archived` | Архив. Старые задания, скрытые из основных списков |

## 11. Чат (Chat)

### 11.1 Условия открытия чата

Чат между заказчиком и исполнителем открывается **только после назначения исполнителя** на задание, то есть когда статус задания переходит в `assigned`.

### 11.2 Структура сообщения

| Поле | Тип | Описание |
|------|-----|----------|
| `id` | INTEGER PK | Уникальный идентификатор |
| `task_id` | INTEGER FK | Задание, к которому привязан чат |
| `sender_id` | INTEGER FK | Отправитель (users.id) |
| `message` | TEXT | Текст сообщения |
| `read_at` | TEXT (ISO 8601) | Время прочтения (nullable) |
| `created_at` | TEXT (ISO 8601) | Время отправки |

### 11.3 Правила доступа

| Действие | Кто может |
|----------|-----------|
| Просмотр списка чатов | Аутентифицированный пользователь (видит только свои чаты) |
| Просмотр сообщений в чате | Только участники чата (заказчик и исполнитель данного задания) |
| Отправка сообщения | Только участники чата |
| Отметка о прочтении | Автоматически при открытии чата получателем |
| Доступ для админа | **ЗАПРЕЩЕНО**. Админ не может просматривать содержимое чатов (принцип приватности) |

### 11.4 Хранение

Сообщения хранятся **бессрочно** в базе данных. Удаление сообщений не предусмотрено.

### 11.5 Read Receipts (отметки о прочтении)

- Поле `read_at` -- NULL, если сообщение не прочитано
- При открытии чата: все непрочитанные сообщения от собеседника получают `read_at = NOW()`
- В интерфейсе отображается галочка прочтения

### 11.6 Исключение для разрешения споров

В случае открытия спора (`disputed`) админ может **временно** получить доступ к чату для разрешения конфликта. Это решение принимается админом и фиксируется в логах. Данная функциональность является исключением из правила приватности.

## 12. Отзывы (Reviews)

### 12.1 Структура отзыва

| Поле | Тип | Описание |
|------|-----|----------|
| `id` | INTEGER PK | Уникальный идентификатор |
| `task_id` | INTEGER FK | Задание |
| `reviewer_id` | INTEGER FK | Автор отзыва |
| `reviewee_id` | INTEGER FK | Оцениваемый пользователь |
| `rating` | INTEGER | Оценка 1-5 |
| `comment` | TEXT | Текстовый комментарий |
| `is_hidden` | INTEGER (0/1) | Скрыт админом (по умолчанию: 0) |
| `created_at` | TEXT (ISO 8601) | Дата создания |

### 12.2 Правила

| Правило | Описание |
|---------|----------|
| Доступность | Обе стороны могут оставить отзыв после завершения задания (статус `completed`) |
| Один отзыв | Каждый участник может оставить только один отзыв на задание |
| Диапазон оценки | От 1 до 5 звёзд (целое число) |
| Комментарий | Обязательное текстовое поле |
| Постоянность | Отзывы не удаляются, но админ может скрыть некорректные (`is_hidden = 1`) |
| Скрытые отзывы | Скрытые отзывы не учитываются в расчёте рейтинга и не отображаются пользователям |
| Влияние на рейтинг | Каждый новый видимый отзыв пересчитывает средневзвешенный рейтинг пользователя |

### 12.3 Расчёт рейтинга после нового отзыва

```sql
-- Пересчёт рейтинга пользователя
UPDATE client_profiles SET
  rating = (SELECT AVG(rating) FROM reviews WHERE reviewee_id = ? AND is_hidden = 0),
  review_count = (SELECT COUNT(*) FROM reviews WHERE reviewee_id = ? AND is_hidden = 0)
WHERE user_id = ?;
```

Аналогичная логика для `performer_profiles`.

| Формат имени файла | `{UUID}-{original_filename}` |
| Максимальный размер файла | 10 MB (10 * 1024 * 1024 байт) |
| Middleware | multer (diskStorage) |

| Endpoint скачивания | `GET /api/tasks/:id/files/:fileId/download` |

### 15.4 Структура записи файла в БД (таблица `files`)

| Поле | Тип | Описание |
|------|-----|----------|
| `id` | INTEGER PK | Уникальный идентификатор |
| `entity_type` | TEXT | Тип сущности: `task`, `offer` |
| `entity_id` | INTEGER | ID задания или отклика |
| `user_id` | INTEGER FK | Загрузивший пользователь |
| `filename` | TEXT | Оригинальное имя файла |
| `stored_name` | TEXT | Имя на диске (UUID + filename) |
| `mime_type` | TEXT | MIME-тип файла |
| `size` | INTEGER | Размер в байтах |
| `created_at` | TEXT (ISO 8601) | Дата загрузки |

### 15.5 Допустимые типы файлов

| Категория | Расширения | MIME-типы |
|-----------|-----------|-----------|
| Изображения | .jpg, .jpeg, .png, .gif, .webp | image/jpeg, image/png, image/gif, image/webp |
| Документы | .pdf, .doc, .docx, .txt | application/pdf, application/msword, application/vnd.openxmlformats-officedocument.wordprocessingml.document, text/plain |
| Архивы | .zip, .rar | application/zip, application/x-rar-compressed |

### 15.6 Валидация при загрузке

1. **Проверка MIME-типа** -- файл должен соответствовать допустимому списку
2. **Проверка расширения** -- расширение файла проверяется дополнительно к MIME
3. **Проверка размера** -- не более 10 MB на файл
4. **Проверка количества** -- не более лимита файлов на сущность
5. **Проверка прав** -- только владелец задания/отклика может загружать файлы

### 15.7 Доступ к файлам

- Файлы заданий: доступны заказчику-владельцу, назначенному исполнителю и админу
- Файлы откликов: доступны автору отклика, заказчику задания и админу
- Скачивание через endpoint с заголовком `Content-Disposition: attachment`

## 16. Безопасная сделка (Safe Deal) -- БУДУЩЕЕ

> **ВНИМАНИЕ:** Данный раздел описывает концепцию будущей функциональности. В текущей версии платформы безопасная сделка **НЕ реализована**.

### 16.1 Концепция

Безопасная сделка (эскроу) -- механизм, при котором платформа временно удерживает средства заказчика до подтверждения выполнения работы.

### 16.2 Планируемый процесс

```
1. Заказчик вносит средства на задание → деньги на счёте платформы
2. Исполнитель выполняет работу
3. Заказчик подтверждает приёмку → деньги перечисляются исполнителю
4. Если спор → админ рассматривает историю чата и принимает решение
```

### 16.3 Комиссия

- Минимальная комиссия только для покрытия расходов на обработку платежей
- Не является источником прибыли (прибыль -- CPM-реклама)

### 16.4 Требования к схеме БД

Текущая схема БД должна предусматривать будущие поля:

```sql
-- В таблице tasks (планируется добавить)
-- escrow_amount    REAL      -- Сумма на эскроу
-- escrow_status    TEXT      -- Статус: none, funded, released, refunded, disputed
-- escrow_funded_at TEXT      -- Когда средства внесены
-- escrow_released_at TEXT    -- Когда средства переведены исполнителю

-- Новая таблица transactions (планируется)
-- id, task_id, payer_id, payee_id, amount, type, status, created_at
```

## 19. Безопасность

### 19.1 Хеширование паролей

- Алгоритм: **bcrypt** (bcryptjs)
- Salt rounds: **10**
- Пароли никогда не хранятся в открытом виде
- При аутентификации используется `bcrypt.compare()` для сравнения

### 19.2 JWT-аутентификация

- Stateless-токены (не хранятся на сервере)
- Срок действия: 7 дней
- При каждом запросе проверяется:
  - Валидность подписи токена
  - Срок действия
  - Статус пользователя (не заблокирован ли)

### 19.3 Защита от XSS (Cross-Site Scripting)

- Функция `escHtml()` на фронтенде экранирует все пользовательские данные перед вставкой в DOM:
  ```javascript
  function escHtml(str) {
    const div = document.createElement('div');
    div.textContent = str;
    return div.innerHTML;
  }
  ```
- Все динамические данные проходят через `escHtml()` перед отображением
- Не используется `innerHTML` с пользовательскими данными

### 19.4 SQL-инъекции

- Все SQL-запросы используют **параметризованные запросы** (prepared statements):
  ```javascript
  // Правильно:
  db.prepare('SELECT * FROM users WHERE id = ?').get(userId);

  // Неправильно (ЗАПРЕЩЕНО):
  db.prepare(`SELECT * FROM users WHERE id = ${userId}`).get();
  ```

### 19.5 Валидация загружаемых файлов

- Проверка MIME-типа на сервере (не доверять расширению из клиента)
- Проверка расширения файла
- Проверка размера файла (не более 10 MB)
- Проверка количества файлов на сущность
- Файлы хранятся с UUID-префиксом для предотвращения коллизий и перебора

### 19.6 Защита от CSRF

- В текущей архитектуре (SPA + JWT) CSRF-атаки не актуальны, так как токен передаётся в заголовке `Authorization`, а не в cookie
- CORS настроен для ограничения источников запросов

### 19.7 Блокировка пользователей

- Заблокированный пользователь (`status = 'blocked'`) не может пройти аутентификацию
- Middleware `authenticate` проверяет статус при каждом запросе
- Существующие JWT-токены не отзываются мгновенно (stateless), но проверка статуса при запросе блокирует доступ

### 19.8 Rate Limiting (рекомендация)

Для production-развёртывания рекомендуется добавить:
- `express-rate-limit` для ограничения количества запросов
- Rate limiting на endpoint логина (защита от brute-force)
- Rate limiting на загрузку файлов

## 22. Схема базы данных

### 22.1 ER-диаграмма (текстовое описание)

```
users (1) ──── (1) client_profiles
  │
  └──── (1) performer_profiles
  
users (1) ──── (N) tasks (как client_id)
users (1) ──── (N) tasks (как performer_id, nullable)

tasks (1) ──── (N) offers
tasks (1) ──── (N) messages
tasks (1) ──── (N) reviews

users (1) ──── (N) offers (как performer_id)
users (1) ──── (N) messages (как sender_id)
users (1) ──── (N) reviews (как reviewer_id)
users (1) ──── (N) reviews (как reviewee_id)
users (1) ──── (N) notifications
users (1) ──── (N) reports (как reporter_id)

files ──── tasks | offers (по entity_type + entity_id)
```

### 22.2 DDL (создание таблиц)

```sql
-- Пользователи
CREATE TABLE users (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  email TEXT UNIQUE NOT NULL,
  password_hash TEXT NOT NULL,
  name TEXT NOT NULL,
  role TEXT NOT NULL CHECK(role IN ('client', 'performer', 'admin')),
  avatar TEXT,
  status TEXT NOT NULL DEFAULT 'active' CHECK(status IN ('active', 'blocked')),
  created_at TEXT NOT NULL DEFAULT (datetime('now')),
  updated_at TEXT NOT NULL DEFAULT (datetime('now'))
);

-- Профили заказчиков
CREATE TABLE client_profiles (
  user_id INTEGER PRIMARY KEY REFERENCES users(id),
  company TEXT,
  city TEXT,
  country TEXT,
  bio TEXT,
  website TEXT,
  rating REAL NOT NULL DEFAULT 0,
  total_tasks INTEGER NOT NULL DEFAULT 0,
  completed_tasks INTEGER NOT NULL DEFAULT 0,
  review_count INTEGER NOT NULL DEFAULT 0
);

-- Профили исполнителей
CREATE TABLE performer_profiles (
  user_id INTEGER PRIMARY KEY REFERENCES users(id),
  specialization TEXT,
  skills TEXT DEFAULT '[]',
  experience TEXT,
  hourly_rate REAL,
  availability TEXT NOT NULL DEFAULT 'free' CHECK(availability IN ('free', 'partial', 'busy')),
  languages TEXT,
  portfolio_links TEXT DEFAULT '[]',
  city TEXT,
  country TEXT,
  bio TEXT,
  rating REAL NOT NULL DEFAULT 0,
  review_count INTEGER NOT NULL DEFAULT 0,
  completed_tasks INTEGER NOT NULL DEFAULT 0
);

-- Задания
CREATE TABLE tasks (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  client_id INTEGER NOT NULL REFERENCES users(id),
  performer_id INTEGER REFERENCES users(id),
  title TEXT NOT NULL,
  description TEXT NOT NULL,
  category TEXT NOT NULL CHECK(category IN ('sites','design','ads','bots','automation','texts','presentations','analytics','other')),
  budget_type TEXT NOT NULL CHECK(budget_type IN ('fixed','negotiable','hourly')),
  budget_amount REAL,
  urgency TEXT NOT NULL DEFAULT 'normal' CHECK(urgency IN ('low','normal','high','urgent')),
  deadline TEXT,
  remote_only INTEGER NOT NULL DEFAULT 0,
  status TEXT NOT NULL DEFAULT 'draft' CHECK(status IN ('draft','published','moderation','assigned','in_progress','review','completed','cancelled','disputed','archived')),
  created_at TEXT NOT NULL DEFAULT (datetime('now')),
  updated_at TEXT NOT NULL DEFAULT (datetime('now')),
  published_at TEXT,
  completed_at TEXT
);

-- Отклики
CREATE TABLE offers (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  task_id INTEGER NOT NULL REFERENCES tasks(id),
  performer_id INTEGER NOT NULL REFERENCES users(id),
  message TEXT NOT NULL,
  price REAL NOT NULL,
  estimated_time TEXT,
  includes TEXT,
  questions TEXT,
  status TEXT NOT NULL DEFAULT 'sent' CHECK(status IN ('sent','viewed','shortlisted','accepted','rejected','cancelled')),
  created_at TEXT NOT NULL DEFAULT (datetime('now')),
  updated_at TEXT NOT NULL DEFAULT (datetime('now')),
  UNIQUE(task_id, performer_id)
);

-- Сообщения чата
CREATE TABLE messages (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  task_id INTEGER NOT NULL REFERENCES tasks(id),
  sender_id INTEGER NOT NULL REFERENCES users(id),
  message TEXT NOT NULL,
  read_at TEXT,
  created_at TEXT NOT NULL DEFAULT (datetime('now'))
);

-- Отзывы
CREATE TABLE reviews (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  task_id INTEGER NOT NULL REFERENCES tasks(id),
  reviewer_id INTEGER NOT NULL REFERENCES users(id),
  reviewee_id INTEGER NOT NULL REFERENCES users(id),
  rating INTEGER NOT NULL CHECK(rating BETWEEN 1 AND 5),
  comment TEXT NOT NULL,
  is_hidden INTEGER NOT NULL DEFAULT 0,
  created_at TEXT NOT NULL DEFAULT (datetime('now')),
  UNIQUE(task_id, reviewer_id)
);

-- Уведомления
CREATE TABLE notifications (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id INTEGER NOT NULL REFERENCES users(id),
  type TEXT NOT NULL CHECK(type IN ('welcome','new_offer','offer_accepted','offer_rejected','task_completed','new_message','new_review','system')),
  title TEXT NOT NULL,
  message TEXT NOT NULL,
  data TEXT DEFAULT '{}',

-- Жалобы
CREATE TABLE reports (

CREATE TABLE files (
  id INTEGER PRIMARY KEY AUTOINCREMENT,

  filename TEXT NOT NULL,
  stored_name TEXT NOT NULL,

-- Индексы
CREATE INDEX idx_users_email ON users(email);
CREATE INDEX idx_tasks_client_id ON tasks(client_id);
CREATE INDEX idx_tasks_performer_id ON tasks(performer_id);
CREATE INDEX idx_tasks_status ON tasks(status);
CREATE INDEX idx_tasks_category ON tasks(category);

CREATE INDEX idx_offers_task_id ON offers(task_id);
CREATE INDEX idx_offers_performer_id ON offers(performer_id);
CREATE INDEX idx_messages_task_id ON messages(task_id);
CREATE INDEX idx_messages_sender_id ON messages(sender_id);
CREATE INDEX idx_reviews_reviewee_id ON reviews(reviewee_id);
CREATE INDEX idx_reviews_task_id ON reviews(task_id);
CREATE INDEX idx_notifications_user_id ON notifications(user_id);
CREATE INDEX idx_notifications_is_seen ON notifications(user_id, is_seen);
CREATE INDEX idx_reports_status ON reports(status);
CREATE INDEX idx_files_entity ON files(entity_type, entity_id);
CREATE INDEX idx_performer_profiles_availability ON performer_profiles(availability);

-- Настройки для производительности
PRAGMA journal_mode = WAL;
PRAGMA foreign_keys = ON;
PRAGMA busy_timeout = 5000;
```

## 24. Глоссарий

| Термин | Английский | Определение |
|--------|-----------|-------------|
| Заказчик | Client | Пользователь, который публикует задания и нанимает исполнителей |
| Исполнитель | Performer | Пользователь, который откликается на задания и выполняет работу |
| Задание | Task | Опубликованная задача/проект, требующий выполнения |
| Отклик | Offer | Предложение исполнителя на конкретное задание |
| Шортлист | Shortlist | Список отобранных откликов, которые заказчик рассматривает подробнее |
| Чат | Chat | Приватная переписка между заказчиком и исполнителем по конкретному заданию |
| Отзыв | Review | Оценка и комментарий после завершения задания |
| Жалоба | Report | Сообщение о нарушении правил платформы |
| Безопасная сделка | Safe Deal / Escrow | Механизм удержания средств до подтверждения выполнения (будущее) |
| CPM | Cost Per Mille | Стоимость за 1000 показов рекламы |
| Модерация | Moderation | Проверка задания администратором перед публикацией |
| Рейтинг | Rating | Средневзвешенная оценка пользователя на основе отзывов |
| Аватар | Avatar | Фотография/изображение профиля пользователя |
| Черновик | Draft | Непубликованное задание, доступное только владельцу |
| Архив | Archive | Старые завершённые/отменённые задания, скрытые из основных списков |
| WAL | Write-Ahead Logging | Режим журнала SQLite для улучшения параллельного доступа |
| SPA | Single Page Application | Одностраничное приложение, работающее без перезагрузки страницы |
| JWT | JSON Web Token | Токен аутентификации в формате JSON |
